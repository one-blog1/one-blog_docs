# One Blog 0.18

서비스 안정성을 높인 운영 버전입니다 (2026-10-14). 사용자에게 보이는 화면 변화는 없습니다. 앱을 한 서버 안에서 2개씩 띄워 하나가 멈춰도 서비스가 이어지게 하고, 컨테이너가 쓰는 메모리에 상한을 두었습니다.

- 코드: [one-blog1/one_blog](https://github.com/one-blog1/one_blog) 태그 `v0.18` (`4ae7915`)
- 요구사항 기준: 4.3(확장성), 결정 D-135(무중단 배포)의 확장. DB·화면·앱 기능 변경 없음

## 운영·배포

**한 서버 내 앱 다중화 + 블루-그린 유지** (D-135 확장)
- 한 서버 안에서 색마다 앱을 2개씩 띄우고(블루 8431·8432 / 그린 8433·8434) 8430 프록시(nginx)가 번갈아(round-robin) 보냅니다. 평소 2개가 함께 요청을 받으므로, 한 개가 멈추거나 교체 중이어도 나머지가 받습니다(`proxy_next_upstream`, `max_fails=1 fail_timeout=10s`, `proxy_connect_timeout 2s`).
- 배포는 블루-그린 그대로입니다. 쉬는 색 2개에 새 버전을 띄워 둘 다 `/api/health`를 통과하면 프록시를 그 두 포트로 통째 전환(`nginx -s reload`)하고 옛 색을 내립니다. 2개 중 하나라도 상태 확인에 실패하면 새로 띄운 것만 치우고 지금 버전을 그대로 둡니다.
- 예전 단일 컨테이너(`one-blog`·`one-blog-blue`·`one-blog-green`)가 돌던 서버는 포트가 겹치지 않는 반대 색으로 교체한 뒤 내려, 멈춤 없이 다중화로 넘어갑니다.
- 이것은 요구사항 4.3의 "서버 2대 이상 이중화"(로드밸런서를 둔 여러 대 구성)가 아니라 그 중간 단계인 **한 서버 안 앱 다중화**입니다. 앱 프로세스 하나가 멈추는 것과 배포 중단은 막지만, 서버 자체가 멈추는 것은 막지 못합니다(앱 2개가 같은 서버).
- 로그인(JWT)·업로드 파일(공유 볼륨)·예약 작업(SchedulerLock, SCL-03)은 서버 밖·공유 자원을 쓰므로 앱이 2개여도 그대로 동작합니다. IP별 요청 제한만 앱마다 따로 세어 느슨해질 수 있습니다(공유 저장소는 서버를 여러 대로 늘릴 때 정합니다, 4.3).

**컨테이너 메모리 상한**
- 각 앱 컨테이너를 `--memory=1536m`로 띄웁니다(`APP_MEMORY`로 바꿀 수 있음). 공용 서버에서 컨테이너에 상한이 없으면 `-XX:MaxRAMPercentage=75`가 호스트 전체 메모리를 기준으로 잡혀 앱이 과도한 메모리를 자기 몫으로 인식하는 문제를 막습니다.

## 알려진 제한

[0.17](v0.17.md#알려진-제한) 그대로입니다. 더해:
- 한 서버 안의 다중화라 서버 자체 장애는 막지 못합니다(4.3의 서버 여러 대 이중화는 이후 과제).
- 운영 앱은 아직 `FORWARD_HEADERS_STRATEGY=none`이라 접속 IP를 프록시 주소(127.0.0.1)로 봅니다. 앱이 2개가 되며 IP별 요청 제한이 더 느슨해졌습니다(다음 버전에서 실제 접속 IP를 읽도록 고칠 예정).
