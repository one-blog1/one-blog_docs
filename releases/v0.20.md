- 요구사항 기준: 결정 D-140(배포 단계별 테스트), 기능 명세 [028](../specs/028-ci-test-stages/spec.md). 4장 배포 자동화·무중단 배포, D-117·D-135·D-136. 휴대폰 화면 정리는 hotfix(코드 저장소 PR #13·#14). DB 변경 없음

## 기능·화면

**휴대폰 화면 정리**
- 블로그 관리: 신고 목록이 한 줄로 늘어서 화면이 옆으로 넓어지고 [관리] 창이 화면 밖에 뜨던 문제를 고쳤습니다. 신고·해제 문의는 카드(종류·사유 이름표, 신고된 내용 3줄)로, 휴대폰에서는 멤버 표와 멤버 전체 보기 창도 카드로 보여 줍니다.
- 휴대폰에서 입력칸 글자를 16px로 키워, 아이폰이 입력칸을 누를 때 화면을 확대하지 않습니다.
- 관리자 화면의 표는 칸이 4개 이상이면 휴대폰에서 줄마다 카드로 보여 줍니다.
- 글 본문의 표는 글자를 쪼개지 않고 옆으로 밀어서 봅니다. 약관·방침 표는 칸 최소 폭을 둡니다.
- 프로필: 휴대폰에서 사진을 왼쪽에, 이름·팔로워를 옆에 두고 소개는 상자로, 단추는 한 줄로(차단·신고는 작은 글자) 정리했습니다.
- 글 목록 태그는 휴대폰에서 3개까지 보이고 나머지는 "+N"으로, 긴 태그와 블로그 소개 태그는 말줄임합니다.
- 받은 블로그장 위임 요청은 안내 글을 위에, 단추를 아래에 둡니다.
- 태그 ×, 최근 검색어 칩, 체크박스, 멤버 [관리]를 손가락으로 누르기 쉽게 키웠습니다. 손가락 화면에서는 아이콘 이름표가 누른 뒤 남지 않습니다.

## 운영·배포

**배포 단계별 테스트** (028, D-140)
- CI를 두 단계로 나눴습니다. 기능·hotfix 브랜치 push와 PR은 `unit`(DB 없는 단위 테스트 90개, 1~1.5분), `develop`·`main`에 합쳐지면 `full`(전체 테스트 306개 + E2E 8개 + 커버리지 + SonarQube 품질 게이트 + jar·Docker 실행 확인, 약 7분)이 돕니다.
- PR은 `unit`을 통과해야 합칠 수 있습니다(브랜치 보호 Ruleset, 관리자·Claude 앱은 예외).
- E2E: 실제 브라우저(Playwright)가 핵심 흐름 7개를 누릅니다 — 가입·로그인·로그아웃, 블로그·글·댓글, 권한, 좋아요·수정·삭제, 참여 신청·승인, 에디터로 사진 넣기, 로그인 실패·비밀번호 변경·탈퇴. 실패하면 화면 캡처와 기록(trace)을 결과물로 올립니다.
- SonarQube 정적 분석(`http://s4.java21.net:9000`, 프로젝트 `one-blog`): merge 뒤 `full`에서 분석하고, 품질 게이트를 넘지 못하면 CI가 실패해 `main`이면 배포하지 않습니다. 이번 분석이 기준점입니다.
- 배포: 프록시를 새 버전으로 바꾼 직후 운영 확인(주소 9개)을 하고, 실패하면 프록시를 옛 버전으로 자동으로 되돌린 뒤 배포를 실패로 끝냅니다. 0.20 배포에서 처음 동작했고 통과했습니다.
- 기존 CI가 `gradle | tee` 때문에 테스트 실패를 초록불로 덮던 문제를 고쳤습니다(셸 pipefail). 지금까지의 테스트는 다시 돌려 모두 통과하는 것을 확인했습니다.
- 테스트 이름 규칙: `...IntegrationTest`(DB 필요), `...E2ETest`(브라우저), 나머지는 단위. 실행 방법은 코드 저장소 readme "테스트와 CI".

## 알려진 제한

[0.19](v0.19.md#알려진-제한) 그대로입니다. 더해:
- SonarQube 서버가 Community라 PR은 분석하지 않습니다. 품질 게이트는 merge 뒤에 봅니다.
- 스테이징 서버·카나리 배포는 두지 않았고, 성능·부하 테스트와 운영 모니터링(느린 API·쿼리 기록)은 후속 작업입니다.
- 자동 되돌리기는 배포 직후 확인 주소 9개만 보고, DB 변경은 되돌리지 않습니다.
