# 릴리즈 노트

One Blog는 버전을 올리며 운영합니다 (D-119). 버전마다 이 폴더에 릴리즈 노트를 쓰면 GitHub Actions가 이 저장소의 [Releases](https://github.com/one-blog1/one-blog_docs/releases)에 같은 내용을 올립니다.

## 버전 번호

배포할 때마다 **0.01씩** 올립니다. 바뀐 것의 크기와 관계없이 같습니다 (2026-10-12부터, D-121).

- 점 뒤는 항상 두 자리로 씁니다: 0.13 → 0.14 → … → 0.19 → 0.20 → … → 0.99 → 1.00
- 태그와 릴리즈 노트 파일도 같은 번호: `v0.13`, `v0.13.md`
- 이 규칙 전에 나간 0.1.0·0.2.0·0.21은 0.10·0.11·0.12로 이름을 바꿨습니다(태그·노트 파일·Release 모두). 그다음은 **0.13**부터 0.01씩 올립니다.
- 1.00 전까지는 정식 출시 전 단계로 봅니다. 코드 저장소의 `build.gradle.kts` `version`도 같은 번호로 맞춥니다.

## 순서

버전을 올렸을 때만 배포합니다 (D-120). 태그는 직접 붙이지 않습니다.

**버전은 사용자가 정합니다.** Claude는 사용자가 말할 때만 버전을 올리고, 말하지 않았으면 바뀐 내용에 맞는 버전을 제안한 뒤 올릴지 묻습니다.

1. 코드 저장소 `build.gradle.kts`의 `version`을 새 번호로 바꿔 main에 올립니다 (기능 작업의 마지막 커밋에 함께).
2. 자동으로 진행됩니다: CI → 배포 → 성공하면 코드 저장소에 태그 `v<버전>`(예: `v0.13`). 버전을 바꾸지 않은 push는 CI만 돌고 배포하지 않습니다.
3. 배포 확인: `http://<서버>:8430/api/health`의 `version`이 새 번호인지 봅니다.
4. 이 폴더에 `v<버전>.md`(예: `v0.13.md`)를 만들어 main에 올립니다. 첫 줄은 `# One Blog <버전>`. 형식은 [v0.10.md](v0.10.md)를 따릅니다.
   - 배포한 커밋, 바뀐 것, 보안, 운영·배포, 알려진 제한, 블로그 공지 문구
   - 바뀐 것은 코드 저장소에서 `git log v이전..v새버전`을 보고 정리합니다.
   - 올리면 Actions(Release notes)가 이 저장소에 태그와 Release를 만듭니다. 파일을 고쳐 다시 올리면 Release 본문도 그 내용으로 바뀝니다.
5. 사용자가 느끼는 변화가 있으면 관리자 계정으로 블로그 공지사항에 "블로그 공지 문구"를 올립니다 (관리자 화면 → 공지 작성). 사용자에게 보이지 않는 수정(운영·배포만 바뀐 버전)은 공지하지 않습니다.

## 릴리즈 노트와 공지의 차이

| | 릴리즈 노트 (여기) | 블로그 공지 |
|---|---|---|
| 읽는 사람 | 개발·운영하는 사람 | 서비스 사용자 |
| 내용 | 바뀐 것 전부, 기능 명세·결정 번호, 알려진 제한 | 사용자가 느끼는 변화만, 쉬운 말로 |
| 보안 수정 | 자세히 적어도 됨 (비공개 저장소) | "보안을 강화했어요" 정도로만. 취약점 내용은 적지 않음 |
